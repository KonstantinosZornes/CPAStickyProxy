# StickyProxy：持久化账号代理映射设计

> **状态：已确认，待实现。**
>
> 本设计取代“根据账号 `proxy_url` 与所有代理生成的预期 URL 逐一比对，以判断账号使用哪条代理”的模型。

## 1. 决策

StickyProxy 持久化账号到代理的显式映射，并以它作为账号“已应用哪条 StickyProxy 代理”的唯一来源：

```text
CPA 物理账号 auth_index -> StickyProxy proxy_id
```

页面、按代理筛选和“按代理清除”只查询该映射，**不得**读取或比较 `proxy_url` 来反查代理。

`proxy_url` 仍是 CPA 实际出站配置的写入目标；它不是 StickyProxy 代理归属的诊断依据。

## 2. 背景与目标

当前读取一页账号时，为判断每个账号对应哪条代理，需要：

1. 读取该账号认证文件的 `proxy_url`；
2. 以账号邮箱为每一个已保存代理生成预期最终 URL；
3. 规范化后逐一比较。

这使账号列表、代理状态筛选和定向清除都依赖 URL 反查，代理数量增加时成本和理解难度同步增加。

本设计目标：

- 账号对应的代理可由一次键查询确定；
- 不再为识别代理生成、规范化或比较最终 URL；
- 不保存代理密码、最终 URL、邮箱、稳定 hash 或会话 SID；
- 仍只在明确应用或清除时修改明确选中的 CPA 账号；
- 保持“同一账号可随时改用另一代理”的语义。

## 3. 新模型

### 3.1 术语

| 名称 | 定义 |
| --- | --- |
| **账号代理映射** | StickyProxy 状态中以 `auth_index` 为键、以 `proxy_id` 为值的一条持久化记录。它记录插件最后一次成功为该 CPA 物理认证账号应用的代理。 |
| **已映射代理** | 映射指向的、当前仍存在的代理。页面将其显示为账号已应用的 StickyProxy 代理。 |
| **未映射账号代理** | 账号没有有效映射且 `proxy_url` 非空。它可能是人工配置、历史配置或其他系统写入，StickyProxy 不尝试归属到任何代理。 |
| **孤儿映射** | 映射指向一个已不存在的 `proxy_id`。正常写路径不会产生它；读取时忽略，并在下一次状态写入时清理。 |

`auth_index` 是 CPA 主机 API 用来读取账号、并定位认证文件的标识，故为映射键。邮箱只用于生成写入 `proxy_url` 的平台粘滞身份，绝不写入映射。

### 3.2 状态文件

状态文件新增 `account_proxy_mappings`。代理继续以现有字段保存，代理 ID 仍由平台和规范化基础地址确定性派生。

```json
{
  "proxies": [
    {
      "name": "US_Residential",
      "platform": "decodo",
      "base_url": "http://login:password@gate.decodo.com:7000"
    }
  ],
  "account_proxy_mappings": [
    {
      "auth_index": "codex-alice.json",
      "proxy_id": "px_0123456789abcdef"
    }
  ]
}
```

约束：

- `auth_index` 和 `proxy_id` 必须为非空字符串；
- 一个 `auth_index` 最多一条映射；
- 同一个 `proxy_id` 可被任意多个账号映射；
- 映射中不保存 `proxy_url`、最终 URL、邮箱、用户名、密码、稳定 hash、SID 或写入时间；
- 状态加载拒绝重复 `auth_index`、空字段和格式损坏的映射；
- `proxy_id` 可在加载时暂时没有对应代理，以便安全加载因手工修改留下的旧状态；读取时忽略，下一次状态写入时清理该孤儿映射。

## 4. 读模型和筛选

### 4.1 账号列表

账号列表构建为：

1. 读取 CPA `host.auth.list` 的账号元数据；
2. 一次读取状态中的代理及映射，并建立 `auth_index -> proxy_id`、`proxy_id -> proxy` 索引；
3. 对每个账号按 `auth_index` 查询映射；
4. 映射存在且代理存在时，返回 `sticky_applied`、`proxy_id`、`proxy_name`；
5. 无有效映射时，按需读取该账号认证文件，仅判断 `proxy_url` 是否为空和脱敏展示：空值为 `inherits_system`，非空为 `custom_other`，格式错误为 `invalid_proxy`。

第 5 步不得调用 `Rewrite`、`Canonical`，也不得遍历代理。它不能把一个未映射的 URL 识别回代理。

`sticky_applied` 和 `proxy_id` 筛选只使用映射索引，不需要扫描账号认证文件。筛选 `inherits_system`、`custom_other` 或 `invalid_proxy` 时，仍须读取候选账号的认证文件来区分 `proxy_url` 是否为空或有效；但整个过程不生成预期 URL，也不遍历代理。

普通列表可按当前页读取认证文件，以展示 `masked_proxy_url` 或识别 `inherits_system` 与 `custom_other`。已映射代理的归属不依赖这次读取结果。

### 4.2 状态含义

| 条件 | `proxy_state` | `proxy_id` / `proxy_name` |
| --- | --- | --- |
| 映射存在且代理存在 | `sticky_applied` | 映射代理 |
| 无有效映射，`proxy_url` 为空 | `inherits_system` | 不返回 |
| 无有效映射，`proxy_url` 非空且可解析 | `custom_other` | 不返回 |
| 无有效映射，`proxy_url` 非空但不可解析 | `invalid_proxy` | 不返回 |
| 无邮箱、仅运行时账号或认证文件不可读 | 保持现有不可操作状态 | 不返回 |

这表示 `sticky_applied` 的定义从“URL 可由代理推导”变为“插件持久化映射指向该代理”。外部手动修改 `proxy_url` 不会自动改写或删除映射，也不会触发 URL 反查。

## 5. 操作失败时怎么处理

一次“应用”或“清除”会改两处：

1. CPA 账号文件里的 `proxy_url`，它决定账号实际使用什么代理；
2. StickyProxy 状态文件里的账号代理映射，它决定页面显示账号属于哪条代理。

对每个成功处理的账号，这两处必须保持一致。不能出现“页面说账号已经用了代理 A，但 CPA 实际没有写成功”的情况。

每次操作都按下面的规则执行：

1. 先确认所选账号和代理仍然存在、仍然可操作；
2. 逐个修改所选账号的 `proxy_url`；
3. 某个账号修改失败时，记录该账号的错误，不为它新增或删除映射，然后继续处理下一个账号；
4. 成功修改的账号才加入本次映射变更；
5. 所有账号都尝试完成后，一次性保存成功账号的映射变更；
6. 返回成功数量和失败账号列表。只要有失败，操作结果就是“部分成功”，而不是全部成功。

不会因为一个账号失败而恢复已经成功处理的其他账号。操作者可根据失败列表修复问题后，再次只对失败账号执行操作。

如果映射保存失败，系统返回该错误，且不回滚已经成功写入 CPA 的账号文件。由于没有成功持久化映射，这些账号会暂时显示为“其他账号代理”；修复状态文件问题后，操作员重新应用代理即可建立映射。

### 5.1 应用代理

对本次明确选中的 `auth_index`：

1. 生成并写入该代理的账号最终 `proxy_url`；
2. 将该账号的映射更新或插入为 `{ auth_index, proxy_id }`。

再次应用同一代理且账号的 `proxy_url` 已是本次应写入的地址时，系统不重复写入，计为“已经应用”。如果有人后来手动改过账号的 `proxy_url`，页面仍显示映射中的原代理；操作员再次点击应用时，会把正确地址重新写回。应用另一代理时，只替换这个账号的映射，不影响其他账号。

### 5.2 清除账号代理

对本次明确选中的账号：

1. 清空 CPA `proxy_url`；
2. 删除该账号的映射，无论它原先是否指向某个代理。

### 5.3 按代理清除

对本次明确选中的账号：

1. 仅处理映射的 `proxy_id` 等于操作代理 ID 的账号；
2. 对这些账号清空 CPA `proxy_url`；
3. 删除这些账号的映射。

未映射账号、映射到其他代理的账号以及未选择账号完全不受影响。此操作不读取或比较它们的 `proxy_url`。

### 5.4 编辑和删除代理

代理 ID 取决于平台和基础地址：修改平台或基础地址会得到新的 `proxy_id`。

- 仅修改名称：代理 ID 不变，映射保持；
- 修改平台或基础地址：旧 ID 的所有映射在同一次状态保存中删除；CPA 的既有 `proxy_url` 不被改写；操作者必须显式将账号重新应用到新代理；
- 删除代理：同一次状态保存中删除引用该代理 ID 的全部映射；CPA 的既有 `proxy_url` 不被改写。

这避免让旧映射静默指向一个语义已改变的代理，也避免通过旧 URL 自动重新认领账号。

## 6. 不兼容迁移

这是一项有意的不兼容变更。

新版本使用 `proxies`、`account_proxy_mappings` 和 `proxy_id` 作为持久化字段，并以 `px_` 开头的代理 ID 标识保存的代理。它不读取任何旧状态字段，也不提供状态迁移或旧 ID 兼容层。

升级前，操作员必须备份旧状态文件；升级后应重新添加所需代理并重新应用给账号。CPA 认证文件中的既有 `proxy_url` 保持原样，直到操作员重新应用代理或明确清除账号代理。

因此升级后，非空的历史 URL 会显示为“其他账号代理”，而不是“已应用 StickyProxy 代理”。这不是错误，也不是迁移遗漏，而是不保留旧状态契约的明确结果。

## 7. 接口和实现边界

### 7.1 state 包

`state.Store` 负责校验、读取、按账号查询和原子保存代理与映射。调用方不接触状态文件结构。

建议提供：

```go
type AccountProxyMapping struct {
    AuthIndex string
    ProxyID   string
}

func (s *Store) Snapshot() ([]domain.Proxy, []AccountProxyMapping, error)
func (s *Store) UpdateMappings(upserts []AccountProxyMapping, deletes []string) error
```

同步操作需要在一次状态写入中应用一批映射变更（新增、更新或删除）；实际 API 可以采用更窄的批量变更类型，但不得逐账号落盘。

### 7.2 accounts 包

`accounts.List` 和 `ResolveFilteredSelection` 接收映射索引或快照，而非仅代理列表。`classify` 改为查询映射，不再依赖 `domain.Rewrite` 或 `domain.Canonical`。

### 7.3 syncer 与 app 包

`syncer` 逐账号读取和写入 CPA 认证文件，并收集失败账号后继续处理。`app` 在持有 `SyncMu` 时协调 `syncer` 和 `Store` 的单次映射写入：只有 CPA 写入成功的账号才更新映射。

## 8. 验收标准

1. 账号列表识别已应用代理时，不调用 `domain.Rewrite`、`domain.Canonical`，也不遍历代理。
2. 对 10,000 个账号、100 个代理按 `proxy_id` 筛选时，不读取账号认证文件，不生成 1,000,000 个预期 URL。
3. 应用代理成功后，CPA `proxy_url` 与该账号的 `proxy_id` 映射同时可见。
4. 某个 CPA 账号写入失败时，其余账号继续处理；失败账号的映射不变，成功账号的映射正确更新，并返回失败账号列表。
5. 映射保存失败时，不写入新映射，也不回滚已成功修改的 CPA 账号；操作返回明确错误，操作员重新应用后可补建映射。
6. 清除账号代理会删除选中账号的映射；按代理清除只删除选中且映射到该代理的账号。
7. 修改代理基础地址、平台或删除代理后，关联映射被删除，原账号 `proxy_url` 不被自动重写或清空。
8. 旧状态字段会被拒绝而不会被静默读取；操作员备份后重新添加代理并重新应用，账号才显示为 `sticky_applied`。
9. 状态文件、HTTP 响应、浏览器状态和日志均不包含最终代理 URL、账号邮箱、稳定 hash、用户名或密码。
